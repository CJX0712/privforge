# ADR-001: Domain selection -- Differential Privacy for ML

- Status: Accepted
- Date: 2026

## Context

PrivForge needed a research/engineering domain that is (a) genuinely underserved by
turnkey tooling, (b) high-impact for real deployments, and (c) self-contained enough
to ship a correct, auditable implementation on numpy/scipy without a heavy deep
learning stack.

Candidate domains considered:

- **Federated learning / secure aggregation.** Well-covered by mature frameworks
  (TensorFlow Federated, PySyft). Adds a distributed-systems surface (comms,
  orchestration, device heterogeneity) that dwarfs the privacy math and pulls the
  project away from a verifiable core.
- **Secure multiparty computation / HE.** Powerful but enormously heavy; the
  engineering cost is in the crypto/transport layer, not in algorithm novelty, and
  it is hard to validate privacy accounting end-to-end in this environment.
- **Differential privacy for ML (chosen).** The core objects -- mechanisms, RDP
  accountant, DP-SGD, adaptive clipping -- are pure numpy and fully unit-testable,
  yet most open-source DP-SGD implementations get the privacy accounting subtly
  wrong (e.g. choosing `C` from private data without accounting for it). There is a
  clear, defensible original contribution: a clip norm that adapts via a DP
  mechanism while staying *decoupled* from the privacy ledger.

## Decision

Build a self-contained DP-ML system around a hand-written DP-SGD plus an adaptive
clipping kernel, rather than wrapping an existing framework. Use `diffprivlib` only
as a Tier-0 reference/cross-check for the mechanism and accountant layers (it is
BSD-3, pure numpy/scipy/sklearn, and ships a py3.13 wheel), not as the algorithm
implementation.

Rationale for "build, don't wrap":

- Opacus / PyTorch-Privacy / TF-Privacy are tied to deep-learning training loops and
  large GPU-oriented wheels; this is a tabular/linear-model system on CPU-only
  Windows.
- Wrapping a framework would hide the privacy accounting behind someone else's
  loop, making the INV-13 decoupling property impossible to guarantee or test.
- The original contribution (AdaClip-Budget) requires controlling the exact noise
  scale and ledger, which only a self-written optimizer provides.

## Consequences

Positive:

- A compact, fully testable core (`core`/`domain`/`training`) with no GPU or torch
  dependency.
- Privacy claims are auditable line-by-line and locked by INV-1..INV-23.

Negative / trade-offs:

- We reimplement mechanisms and the RDP accountant that frameworks already provide;
  mitigated by cross-checking against `diffprivlib` (INV-9).
- We deliberately do **not** claim novelty for the AQUA-DP pipeline name; it is an
  orchestration label only (architecture.md section 8).
